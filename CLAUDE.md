# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project direction

Originally scoped as a habit/exercise/nutrient tracker ("life-tracker"); now **nutrients only**. The app is a single-page calculator, not a logger: the user selects meals from the DB and sees the combined macros/minerals/vitamins against DRI targets. Selection is ephemeral UI state — no dates, no food log, no persistence of selections.

## Layout

- `LifeTracker.slnx` — .NET solution containing `Backend`, `CLI`, `Tests` (all .NET 10).
- `Backend/` — ASP.NET Core Web API + EF Core (SQL Server).
- `Frontend/` — React 19 + TypeScript + Vite + Tailwind v4, React Compiler enabled via Babel. Not part of the .NET solution.
- `CLI/` — early console UI stub; collects input but is not wired to anything.
- `Tests/` — Reqnroll (Gherkin/BDD) on xUnit, referencing `Backend` directly.

## Commands

Backend (from repo root):
```
dotnet build LifeTracker.slnx
dotnet run --project Backend --launch-profile http     # http://localhost:5020; Scalar API docs at /scalar in Development
dotnet ef migrations add <Name> --project Backend
dotnet ef database update --project Backend
```

Tests:
```
dotnet test Tests
dotnet test Tests --filter "Category=dri"               # Reqnroll maps @tags to xUnit categories
```
`Tests/Features/*.feature.cs` are generated by Reqnroll from the `.feature` files — edit the `.feature` file, not the generated code.

Frontend (from `Frontend/`):
```
npm run dev              # Vite dev server; proxies /api -> http://localhost:5020
npm run build            # tsc -b && vite build
npm run lint
npm run generate-types   # regenerate src/types/api.ts from the backend OpenAPI doc
```

## Configuration / secrets

`appsettings*.json` contain no connection string or API key. The backend expects, via user secrets (`UserSecretsId` in `Backend.csproj`) or environment:
- `ConnectionStrings:DefaultConnection` — SQL Server
- `UsdaApiKey` — USDA FoodData Central API key

```
dotnet user-secrets set "UsdaApiKey" "<key>" --project Backend
```

## Architecture

**Backend** follows Controller → Service (interface + impl, registered scoped in `Program.cs`) → `AppDbContext`. Routes are `api/[controller]` (`/api/dri`, `/api/ingredients`, `/api/meals`).

- **Data model:** `Ingredient` has one-to-one `Macro`, `Mineral`, `Vitamin` rows (unique `IngredientId` index each). `Meal` ↔ `Ingredient` is many-to-many through `MealIngredient` (with `QuantityUsed`). All decimals use precision `(19, 8)` via `ConfigureConventions`. EF migrations in `Backend/Migrations` are the source of truth; `Backend/schema.sql` is an older hand-written schema and is out of date (e.g. decimal precisions).
- **Nutrient values are per 100 g/ml.** `MealService.CalculateNutrients` scales each ingredient by `QuantityUsed / 100`, sums, divides by `Servings`, and rounds (2 dp for macros, 4 dp for micronutrients). Nullable nutrients stay `null` unless at least one ingredient has a value.
- **`Backend/Constants/Nutrients.cs` is the central nutrient registry**: each `Nutrient` holds its DRI (`Recommended`/`UpperLimit`), `Unit`, and USDA nutrient id. `DriService` enumerates its public static fields via reflection, so adding a field changes the `/api/dri` output (and the count asserted in `Tests/Features/Dri.feature`). Helper entries like `VitaminK1`/`VitaminK2` exist only for USDA lookup.
- **Ingredient creation (`IngredientService.AddAsync`)** mixes two sources: macros, energy and salt come from the request DTO (label values); micronutrients are fetched from USDA FoodData Central when `UsdaId` is supplied, matched by `Nutrient.UsdaId`. Salt is split into sodium/chloride by mass fraction; vitamin K is the sum of the K1/K1-dihydro/K2 USDA entries. `UsdaService` swallows errors and returns `null`, leaving micronutrients empty.
- Adding a new nutrient touches: `Nutrients.cs`, the relevant model (`Macro`/`Mineral`/`Vitamin`) + migration, `NutrientDto`, `IngredientService.AddAsync`, and `MealService.CalculateNutrients`.

**Frontend ↔ backend type sharing:** `Microsoft.Extensions.ApiDescription.Server` emits the OpenAPI document to `Backend/obj/Backend.json` on backend build. `npm run generate-types` turns that into `Frontend/src/types/api.ts` (generated — don't edit), and `src/types/index.ts` re-exports friendly aliases (`Dri`, `Meal`). After changing DTOs: build the backend, then regenerate types.

**Frontend state:** `App.tsx` fetches `/api/dri` and `/api/meals` once on mount into a single `AppContext` (`useAppContext()`); components read from there. No router — it's a single view.

**npm:** there's an existing peer-dependency conflict (`openapi-typescript` wants TypeScript 5, the project uses 6), so `npm install`/`uninstall` need `--legacy-peer-deps`.

## Style

- Prettier (`Frontend/.prettierrc`): 4-space indent, no trailing commas.
- Existing code keeps imports, object properties, JSX props, JSON keys, CSS properties, and Tailwind classes (variant-prefixed like `md:` sort by their full string) sorted alphabetically — follow that.
- C#: primary constructors for DI, file-scoped namespaces, collection expressions (`[.. x]`).
